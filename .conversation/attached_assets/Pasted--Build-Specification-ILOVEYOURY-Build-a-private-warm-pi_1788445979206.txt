# Build Specification — ILOVEYOURY!!!

Build a private, warm, pink-themed personal website for my girlfriend called **“ILOVEYOURY!!!”**.

The website should feel like a cozy digital space made specifically for her: soft, warm, romantic, clean, organized, and easy on the eyes. Avoid making it overly flashy or childish. Use a polished modern UI with rounded cards, soft shadows, subtle animations, pink/warm cream tones, and comfortable typography.

The application must be responsive and work well on desktop and mobile.

---

## 1. Overall Application Structure

Create a responsive web application with:

* A persistent navigation bar.
* A heart-shaped logo containing a **🌷 pink tulip emoji**.
* Logo text: **ILOVEYOURY!!!**
* Three main tabs:

  1. **Feed**
  2. **Scheduler**
  3. **Wallet**
* Mobile-friendly navigation.
* Smooth transitions between tabs without unnecessarily reloading the page.
* Modal/pop-up interfaces for creation and editing.
* Persistent data storage using Supabase.
* Frontend deployable through Vercel.
* Backend/API services deployable through Render.
* Entire project organized for GitHub and DevOps workflows.

The visual language should consistently use:

* Soft pinks
* Warm cream/off-white backgrounds
* Gentle darker pink accents
* Rounded UI components
* Soft borders and shadows
* Heart/tulip/flower-inspired decorative details
* Minimal visual clutter

Do not sacrifice usability for aesthetics.

---

# TAB 1 — FEED

The Feed is a chronological collection of letters.

## Feed Layout

Display letters as vertically stacked cards.

Each letter card should contain:

* Letter title
* Date posted
* Optional tags
* Rich-text letter content
* Optional small decorative elements
* Edit/delete controls only where appropriate for the owner

Newest letters should appear first.

The feed should be scrollable and pleasant to read, with generous spacing and a comfortable reading width.

## Add Letter

Include an **Upload Letter** button.

When the button is clicked:

1. Display a PIN-entry modal.
2. Require the PIN:

**091425**

3. Do not immediately expose the letter editor before the PIN is successfully verified.
4. If the PIN is incorrect, show a clear but gentle error message.
5. Do not reveal the correct PIN in the UI.

After successful PIN verification, open a second modal containing a rich-text editor.

## Letter Editor

The rich-text editor should support common formatting such as:

* Bold
* Italic
* Underline
* Headings
* Paragraphs
* Bulleted lists
* Numbered lists
* Text alignment
* Links
* Quotes
* Undo/redo

Allow the creator to enter:

* Letter title
* Letter body
* Optional tags

Provide:

* Cancel
* Save/Post

buttons.

After pressing **Post**, save the letter to Supabase and immediately add it to the Feed.

Letters should persist after refreshing the website or switching devices.

The system should sanitize stored/rendered rich text so arbitrary HTML/scripts cannot be executed.

---

# TAB 2 — SCHEDULER

The Scheduler is intended to help her organize tasks, reminders, and important dates.

Provide three calendar views:

* **Monthly**
* **Weekly**
* **Daily**

Also provide an **Add Reminder** button.

## Add Reminder Modal

When clicked, open a modal where she can create a reminder.

Fields:

* Reminder title
* Description
* Tags
* Start date
* End date
* Start time
* End time

The date/time fields should be optional only where logically appropriate, but a reminder must have enough information to appear correctly on the calendar.

Use the user's local timezone for displaying and storing schedule times.

## Monthly View

The monthly calendar should prioritize visual simplicity.

For each reminder, show:

* Title
* Tags

Do not show the full description in the monthly view.

If there are many reminders on one day, intelligently collapse them and provide a way to view the remaining reminders.

## Weekly View

The weekly view should show:

* Reminder title
* Tags
* Description
* Start/end time
* Duration

Organize reminders according to their dates and times.

## Daily View

The daily view should behave like a timetable.

Display a vertical time-based schedule where reminders are positioned according to their start/end times.

For example:

```text
08:00 ─────────
09:00 ── [Study]
10:00 ─────────
11:00 ── [Appointment]
12:00 ─────────
```

Reminders should visually occupy their appropriate time ranges.

Include navigation for:

* Previous day/week/month
* Current day/week/month
* Next day/week/month

## Reminder Management

Allow reminders to be:

* Created
* Edited
* Deleted
* Viewed in any of the three calendar modes

Consider supporting optional reminder colors/tags so different categories can be visually distinguished.

Design the data model so recurring reminders can be added later without rebuilding the scheduler.

---

# TAB 3 — WALLET

The Wallet tab is a personal finance tracker.

It should allow her to track spending, deposits, withdrawals, individual wallets, and total available money.

The Wallet page should contain:

1. Spending/history graph
2. Total money widget
3. Wallet collection
4. General transaction button

---

## Spending Graph

At the top of the Wallet tab, display a graph showing spending history.

Provide three views:

* **Daily**
* **Weekly**
* **Monthly**

The graph should primarily represent money spent/withdrawn over time.

Allow the user to understand her spending patterns quickly.

The graph should update automatically whenever a transaction is created, edited, or deleted.

Include useful labels such as:

* Amount spent
* Date
* Period total

Keep the graph visually clean and consistent with the pink/warm aesthetic.

---

# Total Money Widget

Outside the individual wallets, display a prominent widget showing:

**Total Money**

This represents the combined current balance of all wallets.

For example:

```text
TOTAL MONEY
₱12,450.00
```

The total should automatically update whenever money is deposited into or withdrawn from any wallet.

Do not allow the total to become inconsistent with the sum of individual wallet balances.

---

# Wallet Bento Section

Display her wallets in a responsive **Bento-style card layout**.

Each wallet card should show:

* Wallet name
* Current balance
* Optional target amount
* Progress toward target, if a target exists

Example:

```text
┌─────────────────────┐
│  💗 Savings         │
│                     │
│  ₱4,500             │
│  Target: ₱10,000    │
│  ███████░░░ 45%     │
└─────────────────────┘
```

The cards should have varied but harmonious sizes while remaining responsive.

---

# Add Wallet

Provide a floating **Add Wallet** button.

Clicking it should open a modal containing:

* Wallet name
* Optional target amount

After creating the wallet, immediately display it in the Wallet Bento section.

Wallets should persist through Supabase.

---

# Individual Wallet Interface

Clicking a wallet card should open a wallet detail modal/page.

Show:

* Wallet name
* Current balance
* Optional target
* Progress toward target
* Transaction history for that wallet

Provide:

* Deposit
* Withdraw

buttons.

Transactions made inside this interface must apply **only to the selected wallet**.

---

# General Deposit / Withdraw

Outside the wallet cards, provide a floating transaction button with:

* Withdraw
* Deposit

When clicked, open a transaction modal.

The modal should allow her to enter:

* Transaction type: Deposit or Withdraw
* Amount
* Where the money was spent/came from
* Optional description
* Date/time
* Optional wallet selection

If she does not select a wallet, the system should still allow the transaction to exist as a general/unassigned transaction.

If she chooses a wallet, the transaction must be associated with that wallet and update that wallet's balance.

For withdrawals, the system should prevent accidental negative balances unless the application explicitly supports overdrafts later.

Use Philippine pesos (₱) as the default currency.

---

# Transaction History

Maintain a complete transaction history.

Each transaction should record:

* Amount
* Deposit/withdrawal type
* Date/time
* Where the money was spent or received
* Optional description
* Associated wallet, if any

Allow transactions to be edited or deleted where appropriate.

Deleting or editing a transaction must correctly recalculate the affected wallet balance and spending statistics.

---

# Data Consistency

The finance system must use transactions as the source of truth.

Do not simply store an independently editable wallet balance that can become inconsistent.

Wallet balance should effectively be calculated from its transaction history:

**Balance = Deposits − Withdrawals**

The total money widget should represent the combined balances of all wallets.

Spending graphs should be calculated from withdrawal/expense transactions.

---

# Supabase Backend

Prepare the project to use Supabase for persistent storage.

Create a clean relational database structure for at least:

### letters

* id
* title
* content
* tags
* created_at
* updated_at

### reminders

* id
* title
* description
* tags
* start_date
* end_date
* start_time
* end_time
* created_at
* updated_at

### wallets

* id
* name
* target_amount
* created_at
* updated_at

### transactions

* id
* wallet_id, nullable
* type
* amount
* merchant_or_source
* description
* transaction_date
* created_at
* updated_at

Use proper foreign keys, indexes, timestamps, validation, and constraints.

Design the schema so additional features can be added later without major restructuring.

---

# Security

The website is intended to be private.

Implement proper authentication/authorization around persistent data rather than relying solely on the front-end.

The **091425 PIN** specifically protects the ability to create letters; it should not be treated as a replacement for database authentication.

Do not expose Supabase service-role credentials in the frontend.

Use environment variables for secrets.

Use Supabase Row Level Security where appropriate.

The Render backend should also validate requests instead of trusting the frontend.

---

# Frontend / Backend Architecture

Structure the project so it can be deployed cleanly as:

### Frontend

**Vercel**

Responsible for:

* UI
* Navigation
* Calendar views
* Wallet visualizations
* Rich-text editor
* Modals
* Client-side interaction

### Backend

**Render**

Responsible for:

* Secure server-side operations where required
* Validation
* Business logic
* Protected endpoints
* Any server-side processing that should not occur in the browser

### Database

**Supabase**

Responsible for:

* Persistent application data
* Authentication
* Row Level Security
* Database queries
* Relationships between wallets and transactions

### Source Control / DevOps

**GitHub**

Include:

* Clean Git repository structure
* `.gitignore`
* `.env.example`
* README
* Development instructions
* Production deployment instructions
* Database migration files
* Supabase schema/migrations
* Separate development and production environment configuration
* GitHub Actions where useful for CI/testing/linting

Never commit real secrets, API keys, passwords, or the production PIN into source control.

---

# Responsive Design

The website must work especially well on mobile because it is intended to be used as a personal everyday application.

Mobile UI should include:

* Touch-friendly buttons
* Bottom navigation or compact navigation when appropriate
* Responsive calendar layouts
* Scrollable timetable
* Responsive wallet Bento cards
* Full-screen or near-full-screen modals when necessary
* Comfortable typography
* Proper handling of small screens

Desktop should take advantage of available space without making the interface feel empty.

---

# UI / UX Details

The application should feel like a **digital love-and-life dashboard** rather than a generic productivity application.

Use subtle details such as:

* Heart-shaped branding
* 🌷 tulip accents
* Soft pink cards
* Warm cream backgrounds
* Rounded corners
* Gentle shadows
* Small hover/tap animations
* Smooth modal transitions
* Pleasant empty states
* Friendly confirmation messages

However, keep the interface practical and uncluttered.

Do not overuse hearts, flowers, gradients, or animations.

The primary goal is:

**Cute + warm + organized + genuinely useful.**

---

# Empty States

Every major section should have a thoughtful empty state.

Examples:

Feed:

> No letters yet.

Scheduler:

> Nothing planned for this day.

Wallet:

> No wallets yet. Create your first one.

These should include a clear action button where appropriate.

---

# Error Handling

Handle:

* Invalid PIN
* Failed database requests
* Network failures
* Invalid transaction amounts
* Withdrawals exceeding available balance
* Invalid dates/times
* Failed letter uploads
* Failed reminder creation
* Failed wallet creation

Show human-readable error messages rather than raw API/database errors.

---

# Final Product Goal

The final application should feel like a small personal digital environment made specifically for her.

She should be able to:

* Open the site and read her letters.
* Add new letters through the PIN-protected editor.
* Organize her life through monthly, weekly, and daily schedules.
* Create reminders with descriptions, tags, dates, and times.
* Track her spending through daily, weekly, and monthly graphs.
* Create multiple wallets.
* Deposit and withdraw money from individual wallets.
* Record general transactions and optionally assign them to wallets.
* See her total money across all wallets.
* Track wallet targets visually.
* Access everything comfortably from both phone and desktop.

Build the application with clean separation between presentation, business logic, database access, authentication, and deployment configuration so the project remains maintainable as more features are added later.
